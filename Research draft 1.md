Task 1: Research – Workflow Management Systems
A workflow describes the sequence of activities, decisions and responsibilities required to complete a business process. A Workflow Management System (WfMS) provides the software infrastructure for defining, executing, coordinating and monitoring these workflows. The Workflow Management Coalition (WfMC) distinguishes particularly clearly between a process definition, which represents what is intended to happen, and a process instance, which represents an actual execution of that definition. A single definition can therefore be reused to create many independent running instances. WFMC
This distinction suggests that a reusable workflow engine should separate design-time information from runtime information. A workflow definition should contain relatively stable information such as activities, ordering and dependencies, transitions, participant or role requirements, time limits and routing rules. A running instance instead requires its own identifier, current state, workflow variables, active activities, assigned participants, timestamps, outcomes and execution history. Modern systems such as Camunda reinforce this separation: deployed process definitions are versioned, while each process instance represents one particular execution and retains information identifying the definition and version from which it originated. WFMC
An activity represents a logical unit of work. At runtime, activities create activity or task instances, and human work may be represented as work items/user tasks that can be allocated to participants. The WfMC model allows participants to represent humans, organisational units, roles or resources; abstract roles can then be resolved to actual users at runtime. WFMC Camunda similarly supports an assignee as well as candidate users and candidate groups. Workflow execution also involves decisions and exceptional paths. An activity may be approved or rejected, causing different transitions to become available, while deadlines may trigger escalation or alternative processing. Dependencies determine which work can begin, and events such as task completion, messages, timers and failures can cause execution to continue. Failures should not simply be treated as fatal program errors. Real workflow systems support configurable handling such as retries, alternative/error paths and operator intervention. For example, AWS Step Functions provides configurable retry and catch behaviour, while Camunda creates incidents when an execution cannot progress after certain failures. AWS Documentation
Real processes can also be hierarchical. A workflow may contain individual activities as well as reusable sub-processes or child workflows. Temporal, for example, describes workflows as composite operations consisting of activities and other child workflows. Temporal Documentation This suggests that nested workflow elements should ideally share a common abstraction so that simple and composite activities can be handled consistently. This is closely related to the Composite design principle studied in COS 214, where individual objects and compositions are represented uniformly in a tree structure.     L10-CompositeSlides
Workflow systems must also interact with the outside world. Activities may invoke applications, APIs, services or other workflows rather than performing all business operations themselves. The WfMC reference architecture explicitly separates workflow management from invoked applications, participants, work-list handling and external software. WFMC A reusable TIVIDY engine should therefore coordinate external operations through stable interfaces instead of depending directly on specific applications.
Finally, history and monitoring are core responsibilities. Workflow systems record state changes, task results, failures and other execution events so that administrators can determine what happened and inspect workflows currently in progress. AWS Step Functions, for example, exposes execution status, state transitions and individual state inputs and outputs. AWS Documentation Temporal maintains an event history from which workflow state can even be reconstructed after failure. Temporal Documentation These mechanisms support auditing, debugging, monitoring and reporting.
An important consequence is that change should occur at defined variation points rather than throughout the workflow engine. Routing rules, assignment policies, escalation behaviour, failure/retry policies, external integrations and activity implementations are likely to vary between processes, whereas execution, lifecycle management, history and monitoring are common engine responsibilities.
